# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
pnpm install        # pnpm only (packageManager is pinned in package.json)
pnpm run dev        # Vite dev server on :3000, served under /millisalary/ (opens a browser)
pnpm run dev:host   # same, bound to 0.0.0.0 for testing on a phone
pnpm run build      # tsc -b (the only type check) + vite build into build/
pnpm run analyze    # same build plus bundle-stats.html (gitignored treemap with gzip/brotli sizes)
pnpm run preview    # serve build/ — use this to test the service worker / install flow
pnpm run lint       # eslint over **/*.ts(x)
pnpm run deploy     # build, then gh-pages pushes build/ to the gh-pages branch
```

- Bundle layout (re-check with `pnpm run analyze` after adding a dependency): the `index` chunk is the main screen, `vendor` is React (`manualChunks`, so an app-only deploy doesn't make the service worker download it again), the pushed screens (Settings, Breakdown and their shared `NavScreen` chunk) and the Install sheet are `React.lazy` chunks that load during the first render, and Amplitude (`amplitudeClient`) plus session replay's rrweb chunks load once the browser is idle. Keep heavy dependencies out of the main screen's imports.
- `swift scripts/generate-startup-images.swift` regenerates `public/splash/` (macOS only, no dependencies) and prints the `<link>` tags for `index.html`; run it after changing the face, its size or the theme backgrounds.
- There is no test suite. Verify changes in the running app; `.claude/launch.json` defines a `millisalary-dev` preview server on port 5174.
- Lint baseline: 0 errors and 1 `react-refresh/only-export-components` warning in the generated `ui/button.tsx` (standard shadcn output). Anything beyond that is a regression.
- `pnpm run deploy` (not `pnpm deploy`, which is pnpm's own workspace command) publishes to https://nalezhytyi.github.io/millisalary/ (Pages takes ~1 min to pick it up). Never `git push` or deploy without the user's explicit approval for that specific push/deploy.
- pnpm specifics: it does not run `pre*`/`post*` scripts, so `deploy` builds explicitly; install scripts only run for packages in `pnpm.onlyBuiltDependencies` (`esbuild`); and `node_modules` is strict, so every import needs a declared dependency — e.g. `workbox-window` is a devDependency because `virtual:pwa-register` imports it.
- Prettier runs `prettier-plugin-tailwindcss` 0.7.x with `tailwindStylesheet: ./src/index.css` in `.prettierrc` (needed to sort Tailwind v4 theme classes); 0.8.1 crashed intermittently with `e.charAt is not a function`.
- Commit with the repo-local git identity (`nalezhytyi`), not the global work identity. Commit messages use Conventional Commits with a lowercase scope, e.g. `fix(pwa): …`, `feat(timepicker): …`.

## Architecture

Single-page React 19 + TypeScript + Tailwind v4 + shadcn/ui (Radix) app, no router and no global state library. Everything is deployed under the `/millisalary/` base path (`vite.config.ts` `base`, manifest `scope`/`start_url`/`id`).

**State flows through one hook.** `useAppState` (`src/hooks/useAppState.ts`) owns every setting and every change handler; `App.tsx` destructures it and passes props down to presentational components. Settings persist via `useLocalStorage` (JSON in `localStorage`, keys: `monthlySalary`, `monthlySalaryCurrency`, `earningsCurrency`, `workingHoursPerDay`, `workingDays`, `payday`, `startHour`, `endHour`, `selectedPeriod` (validated with `isPeriod`, falls back to `day`), `theme`, `installBannerHidden` (set by `useInstallPrompt`), plus `exchangeRates` (last known rate per `FROM>TO` pair, written by `useEarnings`); `background` and `isInputsCollapsed` are legacy and removed on startup by `removeLegacyStorageKeys`). Start/end times are stored as `"HH:mm"` strings and re-anchored to today on load; components and calculations work with `Date | null`, converted by `formatTimeInputValue` / `parseTimeInputValue` in `src/utils/salaryForm.ts`.

**Coupled schedule fields:** changing Start moves End forward by `workingHoursPerDay`; changing End recomputes `workingHoursPerDay` from the range; an End earlier than Start pulls Start back to it; editing hours/day moves End.

**Earnings model:** `calculateEarnings(now, settings)` in `src/utils/calculations.ts` is a pure function returning `{ hour, day, week, month, year }` (each `{ earned, total }`), `rates` (per second/minute/hour/day) and `nextPayday`; `useEarnings` calls it every 100 ms with dayjs. Business days are Mon–Fri and only count while the month has scheduled working days left (`workingDays`); a day earns `monthlySalary / workingDays` spread over the start–end window, which is anchored to today (stored times can be from an earlier day). Week = Mon–Sun with a 5-day total; year = completed months in full plus the current one; "this hour" is the part of the current clock hour inside the window. Payday is a day of month (1–31, clamped to the month length). The exchange rate is fetched from exchangerate-api.com (`src/api.ts`) whenever either currency changes and multiplies every amount; a rate only applies to the pair it was fetched for (stale responses are dropped, the same currency is always 1, and the cached `exchangeRates` entry covers reloads and offline launches). The 100 ms tick skips the state update when no number changed, and the `useAppState` handlers are `useCallback`s so the memoized screens don't re-render with it. Formatting uses the `uk-UA` locale with `currencyDisplay: 'narrowSymbol'` (₴, $, €, zł, Kč, lei — plain `symbol` printed "грн" in Chromium but "₴" in WebKit, and the ISO code for USD) in `formatCurrency` / `formatCurrencyParts` in the same file.

**Analytics:** `initAmplitude()` runs from `main.tsx` once the browser is idle after the first render and lazy-loads `src/amplitudeClient.ts` (the SDK with autocapture + session replay at 100%), the only module that may import `@amplitude/*`, so it stays out of the main chunk. `trackAmplitudeEvent` is a no-op until init finishes. User-facing handlers in `useAppState`/`useTheme`/`useInstallPrompt` emit snake_case events: `settings_clicked` (`source: header | setup_hint | history`, the last when the browser goes forward to Settings), `settings_closed` / `breakdown_opened` / `breakdown_closed` (closes carry `duration_ms` and `method`: `back_button | escape | history`, plus `save | discard` for Settings), `settings_saved` (`changed_fields`), `settings_discarded`, `period_changed`, `theme_changed`, `salary_input_blurred`, `salary_currency_changed`, `earnings_currency_changed`, `workday_start_time_changed`, `workday_end_time_changed`, `working_days_changed` / `working_hours_per_day_changed` / `payday_changed`, which fire on save, once for each field that changed (`salary_input_blurred` keeps its old name), and the install banner's `install_banner_clicked` / `install_banner_dismissed` (`platform: ios | android`), `install_prompt_result` (`outcome`) and `app_installed`. New settings and UI should follow that pattern. Events sent before init finishes are dropped, so don't track on first render.

**UI and theme:** the main screen is the header (round glass Breakdown button on the left, Settings on the right), `EarningsDial`, `StatsRow`, a `PeriodTabs` segmented control and `SetupHint` when no salary is set. Settings and Breakdown are pushed full-screen pages (`SettingsScreen`, `BreakdownScreen` on `NavScreen`, see Pushed screens); Install is the only bottom sheet (`InstallSheet`, vaul), and `App.tsx` lazy-loads all three so vaul and Radix Dialog stay out of the main chunk. `InstallSheet` is built on the shared `Sheet`, the iOS 27 kit's medium sheet (a content-sized card floating 6pt in from the screen edges with 34pt top and 58pt bottom corners, 58×4 grabber, a glass ✕ close button at 16pt/16pt and a centered title, scrolling body; capped to the centered `max-w-md` column; in dark it uses the elevated `#1c1c1e` sheet / `#2c2c2e` card colors). Lists use `ListGroup` and `ListRow`; numeric settings use `NumberInput`, which keeps the typed text while focused and only commits complete values (not empty, not below `min`), so a field can be cleared or typed through "0" on the way to "0.5". `SegmentedControl` (period and appearance) is a Radix RadioGroup (arrow keys move the selection), not Tabs: a 47pt glass capsule track (the size of the iOS 27 Photos control: a 4pt inset and 17pt labels; `.segmented-track` in `SegmentedControl.css`: 70% white, or 12% in dark, lit rims at the top and bottom, a 6px blur, the solid fill under `prefers-reduced-transparency`) with one thumb (`bg-segment-selected` with a soft shadow) that slides on the snappy spring over 400 ms (`translateX(index × 100%)`, no slide under `prefers-reduced-motion`; the track is `overflow-hidden` because the spring overshoots past the end segments) and a semibold selected label; pressed, the whole control swells to 1.04 over 450 ms and eases back over 600 ms (the buttons' easing). A glass lens for the moving thumb, styled and timed from screen recordings of Telegram's and the Photos app's controls, was built and then rolled back at the user's request on 2026-10-30; only the Photos size and the glass track stayed. `Button` (`ui/button.tsx`) is the iOS 27 kit's set: every button is a pill with a Medium label, variants `prominent` (Glass Prominent as the kit renders it: `--glass-prominent-fill`, the accent in light and `#0082f0` in dark, i.e. the kit's tint burned into its white backing, with lighter 1px rims at the top and bottom from `--glass-prominent-shadow`; disabled it becomes a plain glass pill), `glass`, `destructive` (glass with a red label), `bordered` (kit Bordered, fill-tertiary) and `plain`, sizes `small` 28 / `medium` 34 / `large` 50 / `icon` 44; pressed, a button swells and brightens 10% like an iOS 27 glass button over 450 ms and eases back over 600 ms, on the CSS `ease` curve with no bounce (round `icon` buttons by 1.36, 44 → 60pt glyph included, measured on a native bar button on the iOS 27 simulator; the others by 8%, via `--press-scale`) (it animates the CSS `scale` property, which Tailwind v4's `scale-*` sets, so transitions must list `scale`, not `transform`; under reduced motion it dims to 70% instead; `plain` always dims), disabled shows at 30%; all app buttons use the glass styles (header, bar buttons, Open settings, Install, the discard alert); `cn` (`lib/utils.ts`) is extended so tailwind-merge reads the iOS text styles as font sizes, not colors. `ListGroup` headers are sentence case (17pt semibold), rows are 52pt and grouped cards use `rounded-card` (26pt, measured on the iOS 27 simulator's Settings). `InstallBanner` floats over the header (fixed, `z-40`, under the sheets) in a phone's browser tab only; `useInstallPrompt` decides when: an iPhone in Safari (not other iOS browsers or in-app web views) or an Android phone once Chrome has fired `beforeinstallprompt` (captured at module load, before React mounts), never in standalone. Install calls Chrome's prompt on Android and opens `InstallSheet` on iPhone, Safari's Add to Home Screen steps (Safari 26+ is told apart by `CSS.supports('animation-timeline: scroll()')`, since its UA is frozen at iOS 18). Dismissing, accepting the prompt or opening the sheet once sets `installBannerHidden`, because Safari can't tell whether the app was added. `EarningsDial` animates the arc in `EarningsDial.css`: it grows in on first paint and glides between periods (off under `prefers-reduced-motion`). Its face is `public/images/money-face.webp`, an animated WebP with alpha (288px, 150 frames at 20 ms, 1.3 MB: 3× the 96pt it takes on the splash, about 5× its ~61pt on the dial), which Safari 16+ and Chromium both play, so there is no GIF fallback; under `prefers-reduced-motion` a `<picture>` swaps in the static `money-face.png`. The 512px source GIF is in git history (`git log -- public/images/money-face.gif`, last in `d014099`); the WebP is its frames area-downscaled with premultiplied alpha and encoded with libwebp's `img2webp -min_size -sharp_yuv -lossy -q 65 -m 6 -d 20` (animated WebP codes every frame on its own, so lower resolution is what shrinks it; the encode of 150 frames takes several minutes). The GIF's drop shadow is dithered, isolated opaque black pixels in every frame, and shows as a dotted rim on a light background once the face is drawn at 1:1 device pixels, so those pixels are replaced by a soft black shadow (alpha = box-blurred dot density) before downscaling. The WebP is also the splash's face, and the splash and the dial `<img>` share its URL on purpose (see Splash). Colors are shadcn tokens in `src/index.css` mapped to iOS 27 system colors (`systemGroupedBackground`, `label`, non-opaque `separator`, `systemBlue` `#0088ff` / `#0091ff`, …) for `:root` and `.dark`, with the four system fills (`bg-fill-*`), `--segment-selected` and a `prefers-contrast: more` block with the increased-contrast accents; there is no other palette. The iOS text styles are Tailwind utilities (`text-headline`, `text-body`, `text-callout`, `text-subheadline`, `text-footnote`, `text-caption1/2`, with iOS line height and tracking) in the `@theme` block: use them instead of `text-[17px]`. The `glass` utility (buttons and the install banner only, never lists, sheets or alert platters, so glass is never nested; the segmented control's glass track has its own style) is a `--glass-fill` lens, a vertical gradient that is darker at the top and brighter towards the bottom (measured from the iOS 27 kit's rendered Glass button), with a 6px blur and the `--glass-shadow` edge: in light the kit's grey crescents on the left and right, a 0.5pt `#e8e8e8` ring and a 2% shadow; in dark a bright 1px rim on top and a softer one at the bottom, at the brightness of native iOS 27 glass on black (the kit's own Figma render of dark glass is a near-black disc); it becomes a solid card under `prefers-reduced-transparency`. Bar-button glyphs (back, close, done) are native SF Symbols exported at the 19pt toolbar size (`components/SFSymbol`: `ChevronLeftSymbol`, `XmarkSymbol`, `CheckmarkSymbol`, `currentColor`, sized inline); other icons are Lucide. Glyphs on glass use the kit's vibrant labels (`--glass-label` #1a1a1a / #f5f5f5, disabled `--glass-label-disabled` #bfbfbf in light), not blue. A full WebGL glass UI was tried and rejected on 2026-10-23 (branch deleted), so don't extend glass beyond these and the segmented track (asked for on 2026-10-30) without being asked. `useTheme` keeps `system | light | dark` in `localStorage.theme` and toggles `.dark`, `color-scheme` and the `theme-color` meta; an inline script in `index.html` applies it before first paint (keep both in sync). Native `<select>` and `<input type="time">` stay native on purpose so iOS shows its system wheels.

**Pushed screens:** `NavScreen` is the iOS 27 pushed page Settings and Breakdown are built on. It renders in a portal on `<body>` only while open or closing (never parked off-screen) and makes `#root` inert; it slides in from the right over 0.35 s on `cubic-bezier(0, 0, 0.6, 1)` (the kit's push) while `html[data-nav-screen='open']` shifts `.app-screen` left by 30% and fades it to 80% (under reduced motion the page only fades). The bar is 62pt (8pt below the safe area like the main header, the 44pt glass ‹ with `ChevronLeftSymbol` set 1.33pt left of centre as on Safari's native back button, 10pt under it) with the 17pt semibold title always in the middle (the `h1` that gets focus on open and labels the dialog) and an optional trailing `action`; it has no background or hairline but floats over the scroller with the iOS 27 scroll edge effect (`.nav-scroll-edge` in `index.css`: a gradient from the page color plus a masked 10px blur), and content starts 8pt below it. Esc closes; in an iOS home-screen app the keyboard covers the page without resizing it, so `NavScreen` pads its scroller by `--keyboard-inset` (from `visualViewport`) and centres the focused field. Each open page is a history entry keyed by its title: opening pushes `{ navScreen: title }` (only if the current entry isn't that page's already, so StrictMode's second mount and a page reopened by going forward add nothing), ‹ and Esc first ask `onBeforeClose` and then call `history.back()`, and `popstate` does the close, so the browser's and Android's back close the page too (`method: history`); a back that `onBeforeClose` refuses pushes the entry again. Going forward onto a closed page's entry (Safari's forward swipe shows the page in its transition) reopens it through `onReopen`. When the browser has already animated the back or forward itself (`PopStateEvent.hasUAVisualTransition`: the swipes in Safari and in iOS web apps), nothing slides a second time: `html[data-nav-instant]` is set to `close` or `open`, the page is dropped without its slide-out or shown without its slide-in, and the main screen snaps; the next open or close sets or clears the flag, so it can't linger. Save and Discard close Settings from inside, and the page drops its entry with `history.back()` after its listener is gone. A reload with a page open replaces the stale state, which leaves one extra main-screen entry. A custom back swipe from the left edge (the page following the finger in the installed iOS app) was built and removed on 2026-10-30 at the user's request; don't bring it back unprompted. Settings edits a draft (`utils/settingsDraft.ts`: `with*` helpers keep the coupled schedule fields in step, `getChangedFields` diffs it against storage) that resets on every open; the prominent ✓ is disabled until something changed and saves through `handleSaveSettings`, which writes storage and fires the per-field events; Appearance applies live and is not part of the draft. With unsaved changes ‹, Esc and the browser's back keep the page and open `DiscardAlert` (Radix AlertDialog: 300pt, 34pt corners, two 48pt glass pills, Keep Editing and a red semibold Discard, over `--overlay-alert`), so the Settings chunk pulls in Radix Dialog.

**Splash:** `#splash` in `index.html` (markup, inline styles, `html.splash-active`) paints before any JS: the theme background (`#f2f2f7` / `#000` via `html.dark`, keep in sync with `--background` and `THEME_COLORS`) with the dial face at 96pt in the centre, `z-index: 100`. `src/splash.ts` (`runSplash`, called from `main.tsx`) plays one cycle of the face (3000 ms = 150 frames x 20 ms, counted from `decode()`), waits for React to mount the dial (`[data-dial-face]` on the `EarningsDial` `<img>`, 2 s cap), then flies the splash `<img>` onto the dial's with a Web Animations FLIP (translate + scale, 500 ms) while the background dissolves (300 ms) and removes the splash. A tap skips the rest of the cycle; under `prefers-reduced-motion` the static PNG shows for 800 ms and fades; if the WebP isn't loaded after 1.5 s the PNG is swapped in. The dial's own face stays `visibility: hidden` during the flight, and the landing is seamless because browsers keep one animation clock per image resource, so two `<img>` with the same URL always show the same frame (checked in Chromium by comparing the frames of two images inserted 1.4 s apart; not yet confirmed in iOS Safari). In iOS standalone `#splash` joins the absolute full-screen layers in `index.css`. Haptics were tried and dropped: iOS has no Vibration API and the `<input switch>` trick gave nothing on iOS 26, and Chrome blocks `navigator.vibrate` until a tap. Don't track the splash in Amplitude (it isn't initialised yet).

**Native iOS splash:** `public/splash/` holds `apple-touch-startup-image` PNGs for 13 portrait iPhone sizes in light and dark (`prefers-color-scheme` in the `media` of each `<link>` in `index.html`; the manual theme switch is not seen there). They are generated, not drawn: `swift scripts/generate-startup-images.swift` renders the first frame of `money-face.webp` at 96pt in the centre of the theme background (`FACE_POINTS` and `BACKGROUNDS` must match `#splash` in `index.html`) and prints the `<link>` tags to paste back; add a row to `SCREENS` for a new iPhone size. They are not in the precache: iOS stores them when the app is added to the Home Screen (so an app added earlier keeps the old image until re-added), and they don't need to work offline. Testing in the simulator: Safari's Share > Add to Home Screen did not open its dialog on iOS 26, so the native image itself can only be checked on a real iPhone (add the app to the Home Screen from a LAN `pnpm run dev:host` URL).

**shadcn:** components live in `src/components/ui/` (`components.json`, style `radix-nova`, alias `@/`). The CLI (4.22) writes `import { cn } from "cn"`, which is an unrelated npm package: after every `pnpm dlx shadcn@latest add …` run `grep -rn 'from "cn"' src/`, point those imports at `@/lib/utils` and `pnpm remove cn`.

**Components** each live in their own folder with an `index.ts` re-export and, when needed, a co-located `.css` file for things Tailwind can't express (webkit pseudo-elements, platform workarounds).

## PWA and platform quirks

- `vite-plugin-pwa` (generateSW, `autoUpdate`) builds the manifest from `vite.config.ts`; the service worker registers only in production (`main.tsx`). It precaches the built JS/CSS/HTML, `includeAssets` and the manifest icons; the animated dial face (1.3 MB) is runtime-cached instead (`StaleWhileRevalidate` in the `images` cache, matched by file name in `urlPattern`, so renaming the file means updating that too), which keeps it available offline after one online load. A first visit fetches its images before the worker takes control, so `main.tsx` requests them again through the worker on `controllerchange` (the HTTP cache answers); without that the face only reached the cache on the second visit. Test offline on a fresh origin (e.g. `http://<anything>.localhost:<port>/millisalary/`), since an unregistered worker can linger on the old one. After asset changes, a stale SW cache can hide updates — hard reload or test via `build` + `preview`. In an installed iOS web app a new build appears on the second launch (the first launch serves the cache and installs the new worker).
- **iOS standalone:** an inline script in `index.html` adds `html.ios-standalone` when `navigator.standalone` is true. In that mode the initial containing block is a viewport shorter than the screen (812pt on an 874pt iPhone 17 Pro: screen minus status bar), anchored at the top, and WebKit clips `position: fixed` layers to it. `src/index.css` therefore makes `html` a non-scrolling shell and `body` the scroller, and switches the full-screen layers to absolute, growing them by `env(safe-area-inset-top)`: the main screen (`.app-screen`), the vaul overlay and the vaul sheet content (`[data-slot=drawer-overlay|drawer-content]`; the floating sheet sits 6pt above the physical bottom with its height capped by the containing block, because `dvh` swings between 812 and 874 there) and the pushed page (`.nav-screen-layer`). Any new full-screen fixed layer must join that list. While a sheet is open, Radix's scroll lock sets `body[data-scroll-locked] { position: relative !important }`, which would make the 812pt `body` the sheets' containing block and clip them again — the standalone rule forces it back to static. In that mode the keyboard also covers a page without resizing it, which is why `NavScreen` pads its scroller from `visualViewport` (after the keyboard closes iOS keeps reporting a short visual viewport for a while). Don't size full-height layers with `100vh`; anchor `top`/`bottom` instead, and never park a closed layer off-screen in an absolute box (it widens the document and iOS pans to it). Verified on the iOS 26 and 18.5 simulators; the comments in `index.css` explain each rule.
- **Status bar:** `apple-mobile-web-app-status-bar-style` stays `black-translucent`. On iOS 18.5 and 26 the status-bar text follows the page (dark text over the light theme, white over dark, including a manual Light/Dark override), so no runtime switching is needed. The style is captured at install time (`WebClipStatusBarStyle` in the webclip's `Info.plist`).
- **Native time input** (`TimePicker`): `appearance: none` and `min-width: 0` keep iOS from overflowing the row; `color-scheme` is inherited from `<html>` (set by `useTheme`). In dark mode the Chromium clock icon is forced white with `filter: brightness(0) invert(1)` because Chromium versions disagree on whether `color-scheme` already lightens it. On iOS 26 `<select>` opens the native popup menu and `<input type="time">` the native wheel.
- **Icons:** the master image is `public/images/money-face.png`, which is 433×480 (not square: the face is the 433px circle at the top, the tongue hangs below it). Every icon maps that circle onto a square with the elliptical grid mapping (sampled ~3px inside the rim), so the round face becomes a rounded square while its centre barely moves and the tongue runs off the bottom edge — not a plain stretch or a crop. `apple-touch-icon.png` (180) is that square full bleed and fully opaque: iOS fills transparent corners with white and captures the icon once at "Add to Home Screen", so it can't follow the theme. `favicon.png` (64) rounds the corners (22.5% of the side). The manifest's `pwa-square-*` put the rounded face on the macOS icon grid (824/1024 body, ~10% transparent padding), because macOS draws non-squircle app icons on a plate; `pwa-maskable-512x512.png` is the full-bleed square with `purpose: maskable` for Android launchers.
- Chrome (144+) does not refresh an installed app's icon unless the manifest `icons` entries change (e.g. a new file name). Overwriting the PNGs in place only reaches new installs.
